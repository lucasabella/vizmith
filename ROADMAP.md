# Roadmap

Milestones and the decisions behind them. Task level work lives in issues.

## Decisions made

**The model emits a query IR, not SQL.** The LLM returns a JSON structure describing tables, joins, filters, grouping and aggregation. A deterministic builder compiles that to SQL. This is what makes "the model never emits code that gets executed" true rather than aspirational, and it means the query layer is testable without an LLM call. The cost is expressiveness: anything the IR cannot describe cannot be asked. That is accepted for v1.

**The chart spec is an abstract grammar, not an ECharts config.** Mark plus encoding channels, in the shape of Vega-Lite but without the dependency. The renderer compiles it. An ECharts config would be unreadable in a diff and would weld the project to one rendering library.

**A multi series chart must limit by dimension, not by row.** `limit` caps rows, so on a query grouped by two columns it cuts series members off at an arbitrary point and produces a chart that looks correct and is not. The IR has `limit_by` for that: keep the top N values of the outer dimension, then every row belonging to them. The validator rejects a coloured multi series chart without it. This costs a windowed subquery in the builder at M3, which is cheaper than a wrong answer nobody notices.

**The result set contract.** Query builder, HTTP API and renderer all pass the same thing: an array of plain objects whose keys are exactly the query's output columns, meaning the `as` alias or the last segment of each `select` and `group_by` item, plus every aggregate alias. Column order is stable and set by the builder, so a caller can rely on it, but the renderer addresses columns by name and must not depend on order. A null value in a field bound to `color` is its own series rather than an error or a dropped row. This is written down here because three separate pieces of work depend on it, and whichever lands first would otherwise decide it by accident. The HTTP API therefore declares no response model over the rows: a second serialiser disagrees with the first about a decimal and would hand a total to the chart as text, and what a value looks like is the source's to say rather than the API's. The cost is that the two endpoints publish no response schema, which is worth less than a number that changes type on its way out.

**A value has one shape, whatever source produced the row.** The contract above fixes the keys and their order and used to say nothing about the values, and the two catalogs disagreed about them: DuckDB answers a decimal column with a `Decimal` and a truncated date with a `datetime`, while Unity Catalog answers in text with the types in its manifest and the Databricks catalog converted an integer, a decimal and a boolean back and left a date as the ISO string the API sent. Nothing was broken by that, because one source draws every chart, and the day a second one does the renderer would have to know which source it was talking to, which is the question the catalog interface exists to remove. So every type in the closed set has a shape: `string` is a `str`, `integer` an `int`, `decimal` a `float`, `boolean` a `bool`, `date` a `datetime.date`, `timestamp` a `datetime.datetime`, and a null is `None` whatever the column's type. An array is not in the closed set and cannot be charted, but the profiler's samples arrive in one, and its values carry the same shapes. `SHAPES` in `catalog.py` is that list in code and `conform` is what a source whose client answers in objects rather than in text calls to keep it, so a second connector conforms rather than reinventing this. The cost is a conversion on every value a source returns, which is a fraction of the round trip that fetched it.

**A temporal value is an object in Python and ISO-8601 text on the wire.** The other option was text from the source all the way to the browser, which is one shape end to end and matches what an HTTP response can carry anyway. It was not taken: JSON has no date, so the value becomes text at the edge either way, and text everywhere buys that single shape at the price of every Python caller parsing it back, the eval harness comparing two result sets and a test asserting a month starts on the first among them. So a catalog answers with a `date` or a `datetime` and the API's encoder writes `2024-01-01` or `2024-01-01T00:00:00`. The renderer reads those two forms itself rather than handing them to ECharts, whose parser reads a bare date as UTC and a date with a time as local, which would draw one contract's two forms a timezone apart on one axis; it reads both as local time, so the wall clock the source sent is the one on the axis in every browser. A timestamp carries no zone at all: Unity Catalog sends a TIMESTAMP with a `Z` and a TIMESTAMP_NTZ without one, and both become the same instant in UTC with the zone dropped. The costs are that the wire shape is now the encoder's, so a response model over the rows would quietly change it, which is already why there is none; that a source rendering timestamps in a session timezone reads as UTC here; and that a value cannot say which zone it meant, which is a feature this deliberately does not have.

**A decimal is a float, and that is a real cost.** The closed set folds FLOAT and DOUBLE in with DECIMAL, so no single shape can be exact for the whole type, and handing back a `Decimal` for a DOUBLE would manufacture precision the source never had. A float is the shape the whole type can hold honestly, it is what the statement API's text converts to, and it is what the JSON encoder writes for either. What it costs is that a total summed from exact decimals can differ from the warehouse's own answer in the last digit, which is the kind of thing nobody notices until they do. Money that has to be exact needs the closed set widened so that DECIMAL is its own type with its own shape, rather than this contract loosened so that a column's values differ by source.

**Relationships are catalog metadata, confirmed once, not inferred per query.** Dragging a field into a chart has to produce a join path, and that can only come from three places: the model, a resolver, or nowhere. Asking the model on every drag makes direct manipulation slow and unrepeatable, which removes the reason to offer direct manipulation at all. So the catalog builds a relationship graph when it profiles a source: declared foreign keys are read where they exist, the rest is suggested from column names and types and confirmed by a person once. Joins then resolve as the shortest path through that graph, deterministically and without a model call. The model receives the graph too, so a join it proposes can be checked against something rather than trusted. The cost is a concept the product did not have and a screen to maintain it, and since a lakehouse table carries foreign keys only when somebody declared them by hand, the suggest-and-confirm path is the common case rather than the exception.

**A table is named on up to three levels, and the target source is a warehouse.** Vizmith is aimed at data held in a lakehouse or warehouse, where a table is addressed as `catalog.schema.table`. DuckDB stays as the test harness rather than a destination: it runs in a test with no network and no credentials, which is what keeps the deterministic half of the catalog, the profiler and the query builder testable at all. The spec grammar therefore accepts one to three segments and resolves a column qualifier against any unambiguous suffix, so a local file keeps its bare names and a warehouse gets its full ones. The cost is that every reference now has to be split from the right rather than the left, and that an ambiguous qualifier is an error someone has to read. Deciding this after the query builder existed would have meant changing the SQL generation and the escaping at the same time, which is the one place where getting a name wrong is a security problem rather than a bug.

**A profile is cheap by requirement.** Against an event table of hundreds of millions of rows, a query is billed and a scan per column is not affordable, so profiling one table is one pass over it and a distinct count is approximate where the source offers an approximate function. A profile records whether each figure is exact, because an estimate presented as a fact ends up in a prompt. The cost is a profile that is less precise than it could be on a small table, which is the wrong thing to optimise for. The fixture dataset carries one deliberately larger event table so that this is testable by asserting which queries get emitted rather than by timing them.

**Profiling is SQL that the catalog executes.** The profiler writes one query and the catalog runs it, so a second source means teaching the catalog to execute rather than writing a second profiler. The parts of SQL that differ between sources are a `Dialect` on the catalog: how an identifier is quoted, how a set of distinct values is collected, and the approximate distinct count where the source has one. They are templates rather than function names, because the shape differs as well as the name. This costs a `run` on the catalog interface, which the query builder then shares, since the warehouse round trip belongs to the source rather than to either caller. The alternative was a profiler that knows Unity Catalog, which would have to be written twice the day a second source arrives.

**A table is two statements, not one.** Every column's statistics come from a single pass over the table. Sample values cannot join that query: collecting the distinct values of a column collects all of them, and on a free text column of a hundred million rows that is the table in memory. So samples are a second statement, emitted only after the first has said which columns are below the threshold and covering all of them at once. It is bounded by construction, because every column it touches is already known to hold fewer distinct values than the threshold, and a columnar source reads those columns rather than the table. The cost is a second scan, which is a fixed price rather than one per column, and it buys exact sample values instead of a sketch that would rank values by frequency and vary between runs.

**The fixture data is committed as Parquet, and the database is built from it at test setup.** A `.duckdb` file is not byte identical across versions, so committing one would make the reproducibility test fail for reasons that have nothing to do with the data. Parquet keeps the event table at a couple of megabytes where CSV would be an order of magnitude larger, and it carries types, so the catalog and the profiler read the same types the generator declared. The cost is that byte identity is still tied to the DuckDB version that writes the file, since the writer sets the compression and the metadata. A version bump that changes either means regenerating the files in the same commit, which is visible in review rather than silent.

**Databricks is the only connector, and DuckDB stays as the test harness.** Vizmith reads a lakehouse, so shipping a second connector means maintaining two answers to every question a source can be asked, and the DuckDB one would be the answer nobody runs. The catalog, the profiler and the query builder therefore target Unity Catalog only. DuckDB does not disappear: it writes the fixture Parquet and builds a local database that deterministic tests run against, offline and without credentials. The cost is that a Databricks connector cannot be proven offline. It is covered by recorded Unity Catalog responses, which a live test checks are still true when a workspace is configured, so the fast suite stays honest instead of merely green. Every fixture spec is compiled and run against the warehouse by the same gate, through the query builder and through the HTTP API, because the dialect that ships is the only one a user's chart depends on. Which catalog and schema those tests read comes from the recording rather than from the environment, so configuration pointed at other data cannot silently redirect them. A recorded response is only ever taken from the synthetic fixture dataset.

**A date can be relative, and the builder is the only thing that knows what day it is.** Every filter value was a `scalar`, so every date in a spec was a date somebody wrote down and there was no way to say "since the start of this month" — which is the most common shape of question a tool like this is asked. The second cost is the worse one: a dashboard is specs, holding no rows precisely so that a tile shows what the data says now, and a tile filtered on a literal date says what the data said the day it was saved. It still draws, the number is still plausible, and nothing says it has stopped meaning what it meant, which is the class of failure this whole design exists to prevent.

The rule that nothing a model produces reaches the database unvalidated does not move, so this is a closed set of tokens and not an expression: `now`, `today`, `start_of` a unit, and `ago` a count of units, with the units the truncation set already has. The builder resolves one into the same text a written date arrives as and binds it exactly as it binds a literal, so nothing relative ever reaches the statement and no connector learns anything — a date is already sent as text with a declared type everywhere.

Which clock had to be decided. A warehouse's `current_date` and the server's differ by zone, and a spec that means something different depending on where it was compiled is not the reproducible artefact this design promises, so the server resolves it: the spec on disk stays relative and the statement is absolute. Naive local time rather than UTC, because "today" is the civil day of the person asking and this runs on their machine. A server run somewhere else than the person reading it would answer a different question for part of every day, and that is the cost of the choice rather than an oversight.

Two things the schema and the validator split between them. The schema holds what each token needs, because a missing key is what a model most often gets wrong and an `if` and `then` says which one. The validator holds the other half: a key that is present and means nothing. `{"relative": "now", "unit": "month"}` satisfies every requirement and a model that wrote it believes it asked for the start of the month, so it is refused by name rather than quietly meaning this instant. Months are counted as calendar months and clamped into shorter ones — thirty days before the 31st of March is not "a month ago" to anybody.

**Every value in a query is bound by name, and the marker is dialect shaped.** The builder writes identifiers, the grammar's own keywords and nothing else into a statement. Filter values and both row limits are bound, including values the validator has already accepted, because validation narrows what can be asked and is not what keeps a value out of the statement text. Parameters are named rather than positional and the marker itself sits on `Dialect`, since Unity Catalog's statement execution takes named markers as `:name` while DuckDB reads that as a syntax error and wants `$name`. The cost is a fourth field on `Dialect`, a `run` that takes values alongside the SQL, and a bound number that has to declare a type narrow enough for where it is used, since a warehouse rejects a `BIGINT` marker in a `LIMIT`. A statement API that answers in text also means the Databricks catalog converts values back using the types in its own manifest, so a total reaches a chart as a number rather than a string.

**limit_by re-aggregates the measure with the function that produced it.** Ranking the outer dimension means combining the rows of each outer value, and the rows are already grouped, so the only honest combination is the aggregate's own function: `sum` for `sum`, `count` and `count_distinct`, `min` for `min`, `max` for `max`. `avg` has no such function, since an average of averages is not an average, so ranking by one raises. The cost is that a spec asking for the top countries by average order value is rejected rather than answered. The alternative was a plausible ordering that is quietly wrong, which is the failure `limit_by` exists to prevent. The top values are picked with an ordered `LIMIT` over the distinct outer values rather than a rank window, because a rank includes ties and would return more series than the spec asked for.

**A question with no dimension is one figure, so `x` is optional.** "What is the total revenue" produces a query with one output column and one row. With both `x` and `y` required, the model's only legal answer bound the measure to both, and the renderer drew a bar at 86 million on a value axis 86 million wide: a chart that is not wrong so much as meaningless. The channel was required because every chart has two axes, and the answer to that is that this is not a chart. So `x` is optional, a spec without one draws the measure as a figure, and three things are rejected instead: a query that selects or groups, because a figure needs the one row that only a whole table aggregate guarantees; a colour channel, because one figure has nothing to colour; and the same column bound to `x` and `y`, which is the shape this replaces. The cost is that `mark` says nothing on a figure, the same way `stack` already says nothing on an arc, and that a versioned public schema loosened a requirement, which is the direction that keeps old specs valid.

**Aggregation lives in the query, never in the renderer.** The renderer draws what it is given. This keeps one source of truth for what a number means.

**A row value never becomes markup.** A tooltip is the one place where a value out of the source is written into the interface, and ECharts renders a tooltip as HTML by default, so a formatter that builds a string puts a category name from a warehouse into the document as markup. The tooltip is therefore drawn on the canvas as text, which is `renderMode: "richText"`, and it cannot execute anything a column happens to contain. The cost is that a tooltip is clipped by the edge of the chart rather than floating over the page, and that styling it means ECharts text options rather than CSS. Escaping in the formatter would have been the alternative, which is one forgotten call away from the same hole.

**Schema constrained output is a property of the schema, not only of the endpoint.** An OpenAI-compatible `base_url` says nothing about whether the endpoint accepts a JSON Schema, and accepting one says nothing about accepting the next. OpenAI's structured output covers a subset of the language: measured on 31 July 2026, a live endpoint took a three line object and answered `400 'if' is not permitted` to the spec schema, which uses `if`, `then`, `allOf` and `not` and leaves most properties optional. So the adapter asks with the schema the caller is about to send, and `constrains_output` takes it as an argument rather than owning one, since a probe with a schema nobody sends answers a question nobody asked. A refusal then means what a caller needs it to mean and the prose path takes over, which is the same path an endpoint without schema support gets. Checked in July 2026: vLLM from 0.8.5 and LM Studio take a `json_schema` response format, Ollama's OpenAI-compatible route refuses it and wants its own `format` parameter, and Azure OpenAI runs OpenAI's implementation, so the subset applies there too. `constrains_output` sends one small request and reads the answer: a refusal means no, a timeout or a broken server means the question was not answered and raises rather than reporting no, because reporting no would send a caller down the unconstrained path for a reason that has nothing to do with the endpoint. `strict: false` is not a way around the subset: the endpoint accepts it and stops enforcing the schema, so a minimal request came back as `{"spec_version":"1"}`, which is the unconstrained path with a parameter that promises otherwise. The cost is one billable request per check, and a probe that is no longer trivial, since a compliant answer to the spec schema is a spec shaped object rather than one boolean. That is the price of an answer about the right question. Azure needed a second look and turned out cleaner than assumed: the `/openai/v1/` base URL takes an ordinary bearer key, so it is configuration rather than a second code path, with the deployment name going in the `model` field. The dates in this entry are evidence for the decision and stay as they were measured; what each endpoint does *now* is `docs/compatibility.md`, which carries a last-checked date per row because that is the part that rots.

**The server probes the endpoint once and asks every question the same way after that.** Knowing whether a schema may be sent is a per endpoint fact, and there were two honest places to get it: ask the endpoint on the first question and remember the answer, or a fourth `VIZMITH_MODEL_` variable that states it. The probe wins because the alternative is a value a person can get wrong in the direction that never announces itself: configure no where the endpoint honours a schema and every question is asked in prose, fails validation more often and spends billed retries doing it. It would also leave `constrains_output` with no caller, and deleting it would quietly undo the entry above that says the adapter asks rather than assumes. The cost is one billed request per server start, and an endpoint whose capabilities change is not noticed until a restart. A probe that never got an answer is not remembered, so the next question asks again rather than inheriting a guess.

**A rejected request and an unanswered one are retried by different loops.** `ask.py` retries what the validator rejects: three attempts, each carrying the previous errors back, which is what makes a question converge. What it did not retry was the endpoint failing to answer at all, so one `429` ended the question and the person got "What the model said" with a rate-limit message in it. Rate limiting is the normal condition on a hosted endpoint rather than an exceptional one, and the question most likely to meet one is the question that already needed two attempts. So the adapter sends the same request again, and the two loops do not share a budget: a transport retry is the same prompt because the endpoint would not take it, and a validator attempt is a different prompt because the answer was wrong, and a shared counter would let a rate limit spend a chance the model never got to use. What is sent again is a `429`, a `5xx` and a dropped connection; every other `4xx` is about the request, and the request does not change between attempts. A timeout is not, deliberately: it is the caller's own number and it has already been waited in full, so three attempts at a sixty second setting is a three minute question, which is a worse answer than saying the endpoint did not answer. An endpoint that sends `Retry-After` gets that long rather than the doubling, since it is the one that knows when its limit resets — as a floor rather than an instruction, because a zero, or a date a client whose clock runs fast reads as already past, would otherwise remove the backoff and put three requests to a rate limited endpoint inside a millisecond, which is worse for it than not retrying at all. The header is read as digits or as an HTTP date and as nothing otherwise, which matters because `float` also reads `inf` and `nan`: taken as numbers those are a wait beyond any budget, so a header saying nothing at all would have turned the retries off. If what is asked for is longer than what is left of the total, the question ends there rather than being slept through, because somebody is watching — and the total is per request while the number is chosen for a question, since `ask` sends up to three requests for one question and the first question of a process pays a probe in front of them. The same judgement is what `constrains_output` now reads: it answers False for a request the endpoint refused and raises for one it never answered, and a rate limit is the second of those. Reporting a `429` as "cannot constrain" would send every question for the rest of the process down the unconstrained path over a limit that cleared in a second.

**The model reads the tables the question is about, not the schema.** A prompt carrying every table costs tokens in proportion to the source: measured by building one at several sizes, 150 tables of 30 columns is 275 kB, about 69,000 tokens per attempt and three times that for a question that takes three tries — and past some size the request stops fitting in a context window at all, which arrives as whatever the endpoint says about an oversized request rather than as a sentence anybody can act on. The eight table fixture schema is why this never hurt here. Selection is two cheap rules and a cap: a table is scored on how much of the question its own name and its columns' names account for, anything one hop from a chosen table through a **confirmed** relationship is a candidate below those, and tables are added in that order until the next one would not fit a character budget. A schema whose vocabulary shares nothing with the question sends the largest few rather than nothing, since a prompt with no tables cannot be answered at all. The heading says when the list is a subset and how many were left out, because a model handed four tables and told nothing reads them as the whole source and answers a question about a fifth by inventing it.

The rule that does not move is the join rule: a spec may only join through what the graph confirms, so reach is computed from declared and confirmed relationships only — a table that only a suggestion reaches is not one a correct answer could join through, so it is not one selection makes room for. What this costs is the prefix: instructions and schema are still identical between questions, but the table blocks now depend on the question, so an endpoint that caches prompt prefixes hits a shorter one. That is the trade, and it is smaller than sending a schema nobody asked about. Words are the cheapest rule that works and they cannot bridge a vocabulary gap — a question about "turnover" scores nothing against a table called `orders`. The next step if that shows up in the scores is a first call that sends names and row counts and asks which tables are needed, which is a round trip per question; the eval harness is what says whether it is needed rather than a guess.

**The question goes last, so everything before it can be cached.** A prompt is instructions, then the schema where it is not attached, then the tables, then the question, then the validator's errors on a retry. Everything before the question is byte-identical between two questions over one schema and between two attempts at one question, because the table list sorts, the profile pass keeps that order and the serialisation is deterministic — which is the prefix a provider's prompt cache can hit, and the larger part of what a question costs. Nothing about the code makes that true, so a test builds the prompt for two different questions over the same profiles and asserts the shared prefix ends at the question. The other half of the same saving is that the schema goes in once: an endpoint the probe found honours a JSON Schema receives it as the response format, and the copy in the prose is left out, which is about 1,350 tokens per attempt and up to six per question. The instructions stay either way, because they say what a schema cannot — dimensions go in `group_by` and nothing in `select`, a question with no dimension omits `x`, a colour channel needs `limit_by` — and those are the validator's rules the retry loop converges on.

**One request fills the panel, and what the width should be is measured rather than reasoned.** Listing the tables profiled every one of them and answered with their names, and the panel then asked for each profile back, so a page load paid the freshness check twice per table plus a schema listing per table for the single-table endpoint's 404 check — about 150 source calls on a fifty table schema, 100 of them statements a warehouse bills for, before anybody had asked a question. `/api/tables` answers with the profiles it built either way, which is what the panel reads, and `/api/tables/{name}` stays for a caller that wants one table. A test counts the freshness checks a warm panel load costs, so a change that doubles them again fails rather than being noticed on a bill.

What that leaves is the floor: one freshness check per table per load, and the cold profile behind it. `PROFILE_WORKERS` is eight because eight overlapped the waiting on a fifteen table schema, and that is the only number behind it — nothing says whether sixteen is better or whether it only lengthens the warehouse's queue. `tests/test_profiling_cost.py` is the harness that answers it: wall clock for a cold profile and a warm one at widths 4, 8, 16 and 24, with the freshness, statistics and sample statements broken out so it is clear which dominates each case. It needs a warehouse and skips without one, so it costs CI nothing. The number and the finding belong here once it has been run against a real schema; until then this entry is the question rather than the answer.

**A schema is profiled several tables at a time.** Profiling a table is two warehouse queries, so profiling a schema one table after another is the wait a first question is made of. Measured on a fifteen table schema against a warm 2X-Small warehouse, doing them in sequence took 26 seconds of a 34 second first question, and nearly all of that was waiting rather than scanning, so they run eight at a time. That makes `run` something several threads call at once, which is stated on the catalog interface, because a source whose client cannot be shared has to serialise inside itself rather than making the caller ask. Eight rather than all of them, since a small warehouse queues what it cannot run concurrently and a longer queue is not a faster answer. What this does not touch is a warehouse that has to start first, which is unbounded from here and is why the wait says so. What it costs is paid once rather than per question, which is the entry below.

**The panel is filled from what costs nothing, and the profiles arrive behind it.** Opening the interface against a schema nobody had profiled meant waiting for every table in it: `/api/tables` answers only once `profiles()` has finished, so the first paint waited on the whole schema. Modelled at 152 tables with 400ms on a statement, that is 24.7 seconds of spinner and 456 billed statements before a person sees a table name. The message under the spinner was honest about why, which is not the same as it being the right thing to wait for.

The panel does not need the profiles to be usable. A table row is a name and a count, a column row is a name and a type, and dragging a column into a well reads the type and nothing else — `spec.ts` looks at no other figure to infer an aggregate or a truncation unit. So the tree a person interacts with is `describe`, which is a metadata read that nothing bills for. `/api/shape` answers with that and only that, and `App.tsx` draws the tree from it and then replaces it when `/api/tables` lands. One extra request for the schema, not the fan-out per table that #73 removed; the bulk profile request behind it is unchanged.

Two things the interface has to keep true while it loads, and they are the same mistake in two places. A table's row count comes from a pass over the table, so it arrives late, and showing a zero in the meantime is a claim about the data where the truth is a claim about what has been read — it shows nothing. And a column opened before its profile has landed says the figures have not been read, rather than drawing them as absent: this is the panel whose whole job is to prove what the model was allowed to see, and a blank where a sample list goes reads as a column with no values. `fromShape` and `merged` in `panels/fields.ts` carry both as nulls, which is why they are nulls rather than zeroes.

Beside it, the freshness statement stopped being paid in front of the profile. A table nothing is stored for is going to be profiled whatever the source says about its freshness, so waiting for that answer before starting the scan was a round trip per table in front of a cold read for a decision nobody makes. It is a concurrent start and not a reordering, and that distinction is the correctness of the whole cache: the token has to be taken no later than the scan begins, or a write landing between the two is stored as current and missing. Taken first, that write costs one more profile on the next read; taken second, it is invisible until the table changes again.

What is deliberately not here. `/api/shape` runs at the same pool width the relationship graph uses rather than the wider one #122 proposed: it is the same call against the same control plane, two widths for one operation is two numbers to tune and one of them wrong, and the second caller pays nothing because the source holds a description. And `PROFILE_WORKERS` is untouched — the model says 16 workers takes the cold read to 13.1s and 24 takes it to 9.2s, and it assumes a warehouse that will run them at once, which a small one will not. That number needs the measurement in `tests/test_profiling_cost.py` and a warehouse, not another guess.

**A metadata read is not a statement, so it runs wider.** The entry above bounds the profiler at eight because a small warehouse queues the statements it cannot run at once, and a longer queue is not a faster answer. That reasoning does not reach a listing or a table description: those are calls to the source's control plane, nothing bills for them and no cluster queues them, so the number that bounds them is the source's own rate limit rather than a warehouse's concurrency. They have a width of their own at sixteen. What made this worth separating is where those reads are: the relationship graph is one description per table plus, inside the catalog, one more per table for the declared constraints, and it is rebuilt from nothing on every request that needs it — including `/api/join-path`, which is what a drop calls, so a person dragging a column onto another table waited for a schema's worth of round trips one after another. Modelled at sixty milliseconds a call on a hundred and fifty tables that was eighteen seconds per drag and is now under two. Modelled rather than measured, because the workspace this was written against is fifteen tables and the shape only bites on a large one, so `tests/test_profiling_cost.py` times both shapes against a real source and prints the two numbers. What this entry deliberately did not do is cache it, and the entry below is where that was taken up: holding a column list the way a freshness answer is held makes a first drag as cheap as a second, and the interaction with the profile cache it names — a profile built from a held description stored under a token taken at the same moment, so a column added between the two is missed until the table changed again — is what that entry had to answer before it could be done.

**A profile is cached in a file, keyed on when the source says the table last changed.** Profiles used to be read on the first question and kept for the life of the process, which left two things wrong: a schema that changed underneath a running server was not noticed until somebody restarted it, and every restart re-profiled every table at two billed statements each. A cache fixes both, and where it lives decides which. In the process is what that was, and it keeps paying the warehouse for anything longer lived than a person's own afternoon. On disk it is, in the state directory beside the relationship answers, because those are already there: a person's confirmation of a suggested join cannot live in a process that ends, and a profile has no better claim to one. The cost is a file whose format has to keep working across versions, and it is paid by not paying it — the file carries the shape it was written under and a profile written under another one is dropped rather than migrated, since this is a cache and the cheapest way to change what it holds is one more profile. The key is that modified time plus the sample threshold the profile was built with, because lowering the threshold has to silence samples a stored profile still holds and the threshold is the security boundary rather than a preference. A table the source reports no modified time for is profiled every time and never stored: caching against nothing means caching forever, and a stale profile is the worse of the two failures, since the figures still look like figures and the model reads them as current.

What the modified time is had to be checked against Unity Catalog rather than assumed, because the whole key rests on it. It cannot be the `updated_at` the metastore already carries on a table, which is the field the information schema calls `last_altered` and which `tables.get` returns for free: Databricks document that it tracks the table's structure and does not move for an insert, an update or a delete, so a profile keyed on it would be re-read when somebody renamed a column and never when the data changed, which is the failure this exists to prevent and the one that announces itself least. Their own answer is `lastModified` from `DESCRIBE DETAIL`, and that is what `DatabricksCatalog.modified` reports. The cost is that asking when a table last changed is a statement rather than a free metastore read, paid per table every time the profiles are read. It is a read of the Delta log rather than a pass over the table, so a cache hit trades two scans of an event table for one metadata statement, and it is the only version of this that notices a write at all. `DESCRIBE DETAIL` has gained columns between runtime versions, so `lastModified` is found by name in the statement manifest rather than at a position, and an object it will not describe, a view among them, reports no modified time and is therefore profiled rather than cached. The interface takes it as an opaque token rather than a timestamp, because it is only ever compared with the last one seen and a source whose honest answer is a commit version should not have to dress it up as a clock. `test_the_modified_time_moves_when_the_data_changes` is what says the documented behaviour is still the real one; it needs a workspace, and it creates and drops its own table rather than writing to the fixture schema. The freshness check runs on every read rather than once per process, since a check that is skipped is the stale profile this replaces, and the visible cost of that is that anything reading the whole schema pays one metadata statement per table each time it does: listing the tables, and resolving a join path, which is a drag of a field into a well. What it buys is that a table rewritten while somebody has the interface open is described as it is now. It runs on every read but not on every request, which is the entry below. Reading one table by name reads only that one, because a panel drawing a tree asks per table and a request that profiled the schema to answer for one of them would pay for the schema once per row of the tree.

**A freshness answer is held for a burst, not for a process.** The entry above pays one metadata statement per table every time the profiles are read, and the entry on filling the panel took a page load down to one such read. What neither touches is that a person produces several reads in a row — the panel, then a question, then a drag of a field into a well — seconds apart, each asking the same source the same question about the same tables and getting the same answer. `Held` in `catalog.py` is what the configured source is wrapped in, and it holds each table's answer for thirty seconds, so a burst asks once per table rather than once per table per request. It holds that one question and nothing else: a listing, a description and a statement all have answers that can differ between two calls a second apart. The cost is a table rewritten under a running server being described as it was for at most the window, which is the same trade the cache itself makes, made smaller and given a number — holding it for the life of the process is exactly what the entry above refuses, and a window with a bound on it is not that. Thirty seconds is reasoned rather than measured: it is about how long a person's continuous use of the interface is, and what would tune it is `tests/test_profiling_cost.py` run against a warehouse, which is the same measurement `PROFILE_WORKERS` is still waiting on. That measurement is still waiting, and it is not what moved this: modelling the same read at a hundred and fifty tables — sleeps rather than a warehouse, so it says the shape of the problem and not the constant — said the window was the right idea held against the wrong thing. A constant per answer governs something proportional to the schema: a cold read takes about twenty-five seconds against a thirty second window, so the answers taken at the top of a request were seconds from expiring by the time it finished, and the next request re-read the front of the schema while the back of it was still warm — a hundred and fifty billed statements for a schema nobody changed. So the window covers a burst rather than an answer. A burst is a run of reads of the source with no gap of the hold or more between them, every answer taken in one is held for as long as it runs, and one request therefore cannot expire halfway through the next. A burst runs from its first question to its last answer, and those are two different instants: a statement queued on a cold warehouse takes tens of seconds, so an answer is dated from when it was asked for — otherwise the round trip buys it that much extra life on top of the ceiling, and a burst can lapse underneath a read that began inside it — while what says the burst is still going is that an answer arrived recently. A burst that never goes quiet would hold an answer for as long as somebody kept working, so it cannot reach further than two minutes from its first question to its last answer, and that ceiling is where the harm is now bounded: a table rewritten under a running server is described as it was for at most two minutes while the interface is in use, and for at most the hold after it goes quiet. Two things the ceiling costs, both chosen. A burst dies whole, so the request that lands just after it re-reads every table at once rather than a few at a time — spikier than the window it replaced, and about a quarter of its statements over the same two minutes, which is the trade. And a cold read that takes longer than the ceiling rolls the burst while it is still running, which is this entry's own failure reappearing for a schema several times larger than any that has been measured; so the guarantee above holds up to the ceiling rather than unconditionally, and both costs are reasons to raise that number rather than to hold answers per entry again. The alternative considered was scaling the hold from how long the last full read took, which measures the same thing indirectly and needs a completed read before it knows anything, so the first cold read — the one that hurts — would still be held wrong. A source with no modified time to give is held like any other answer, because a view costs a failed statement to discover that with; it changes nothing about caching the profile, since a profile is never stored against None.

**A table's shape is held longer than its freshness, and its keys arrive with its columns.** The entry on metadata reads left the relationship graph paying for the whole schema on every request that needs it, and the request that needs it most is `/api/join-path`, which is what a drag of a column from a table the query does not already read calls. Two things were being paid. The graph asked the catalog to describe every table and then asked it for the declared foreign keys, which described every table a second time, because a constraint is held on the table that declares it and there is nothing to ask for the set of them. So a description now carries the keys its table declares, since the response that lists a table's columns is the response that carried them all along, and the schema-wide answer is those descriptions rolled up rather than a second pass beside them. That halves the round trips for any caller doing both, and it is a constraint on a second connector rather than a free win: a source that would rather answer the whole schema's constraints in one query has to answer them per table too. Reading them off a description it has already made is what a caller does instead of asking twice, and `Catalog.relationships()` stays for a caller that has no descriptions in hand.

The other is that nothing held the descriptions at all, so a person dragging a second column paid the same schema again. `Held` holds them now, on a window of its own at five minutes rather than the freshness answer's thirty seconds, and the difference in the two numbers is the difference in what moves them: a freshness token moves when somebody writes to the table, which is all day, and a description changes when somebody alters it, which is the day they change it. What made this wait was the interaction that entry names. `profile_table` describes the table it profiles, so a profile built from a description taken before a column was added would be stored under the freshness token taken after it — current, and missing a column, until the table changed again, which is a staleness the profile cache does not otherwise have. The answer is that a description is held under the token that was in hand when it was taken, and a modified answer that differs from it drops the description, which costs nothing because that answer is already being asked for. Unity Catalog's token moves for a definition change as well as for a write, so a table anything profiles is re-described the moment it changes rather than at the end of the window; the window is what bounds a table nothing profiles. A description taken with no token in hand is dropped by the first answer that arrives, which is the safe direction. The cost is a table altered under a running server being described as it was for up to five minutes on the paths that never ask its freshness — the relationship graph, which is names and types, and the builder, which reads a description for the table's qualified name. Neither is a figure a person reads, and a new column reaches the Fields panel through the profiles, which are keyed on the token. The listing is not held, because that is how a table somebody created is noticed and it is one call for the schema rather than one per table. Modelled at sixty milliseconds a call on a hundred and fifty tables, the drag that was eighteen and a half seconds before the pool and under two after it is now under two cold and a listing warm. Modelled rather than measured, again: `tests/test_profiling_cost.py` times the graph one at a time, overlapped and held against a real source and prints the three numbers.

**Where a spec may read is a record every catalog carries, not a method one of them has.** `api.py` opens by promising that a request carries a spec and nothing else, so a client cannot name a database, and what kept that promise was `DatabricksCatalog.qualify` — a method the `Catalog` protocol does not mention, reached only because that connector's own `describe` happened to call it on the way in. Nothing above the source knew the rule existed: `query.py` documented it as a property of an exception type, and no test in the suite ever asked a catalog to refuse anything. The second implementation in the repository already did not keep it — the fixture catalog took the last segment of whatever name it was given and rebuilt it against the schema that does exist, so a spec naming another catalog was answered with this one rather than refused. Harmless against one synthetic schema, and exactly the template four more connectors were about to be written from.

So the rule is `Scope`: the levels a source puts in front of a table, the values that are configured, and the one method that resolves a name against them. Every catalog carries one, and `query.py` resolves a spec's every reference through it before a name reaches a source, which is where the promise is made and the only place a name that came from outside crosses into one. A connector that never learned the rule cannot be pointed outside it by a spec, because it is handed a name that has already been checked. The two halves of the old method separate cleanly: filling in a short name is a convenience the connector still wants for its own calls, and refusing an out-of-scope one is a boundary that is not the connector's to keep. `levels` is carried only so a refusal reads in the source's own words — a catalog and a schema here, a project and a dataset on BigQuery, a schema alone on PostgreSQL — and `values` is the whole of what a name is checked against. The cost is one more field a connector owes, and it is two configured strings rather than a check it could get wrong. `tests/test_scope.py` holds every catalog to it rather than holding one of them to it.

**DuckDB is a source, not only the harness.** The roadmap deferred a second connector until somebody had a reason to run one, and the argument for holding it — one answer per question rather than two, and the second one being the answer nobody exercises — is an argument this repository had already stopped supporting. `FixtureCatalog` was a complete second implementation of the protocol, every deterministic test in the suite ran through it, and the reproducibility test held the two catalogs to one shape for every value. What that left was the worst version of the trade: the tested catalog was the one nobody was allowed to use, and trying Vizmith meant having a workspace, a warehouse and a bill.

So `DuckDBCatalog` ships, and the counter-argument is answered rather than deleted: it stays the thing the suite runs against, so it cannot rot without the suite going red — `tests/test_duckdb.py` compiles and runs every spec the repository ships against a real file, and the result set contract is now asserted against three sources rather than two. It answers two questions differently from a warehouse and both are the interface working rather than bending. It has no freshness token, so `modified` is None, which the protocol already documents as the honest answer and which turns the profile cache off: two statements per table per read, paid against a local file rather than a billed warehouse, which is the case where paying them is nothing. Inventing a token out of the file's own modified time would key a cache on something that does not move when a row inside the file does, which is the exact failure `DESCRIBE DETAIL` is paid for on Databricks to avoid. And its foreign keys are enforced rather than asserted, so a declared relationship there is a fact about the data; the suggest-and-confirm path is unchanged, because a lakehouse still declares almost nothing and the fixture schema declares two of its keys and leaves the rest to inference.

Which source is configuration and never a request, which is the sentence `api.py` opens with, so `VIZMITH_SOURCE` names a kind and `sources/build` is the only place a name in a settings file becomes a catalog. Each connector is a module in `sources/`, imported when it is the configured kind and not before, so a checkout pointed at a warehouse does not install a database engine and one pointed at a file does not pay for the Databricks SDK. `configure` asks the kind first and then only that kind's settings, because a person setting up a local file should not be asked for a warehouse id to leave blank. The cost is what the roadmap said it was — a second thing to keep true, and a settings surface with a branch in it — and what it buys is that almost everybody who finds this repository can now run it.

**Truncation is the source's spelling, and which function it uses follows from the value's shape rather than the column's type.** The builder wrote `date_trunc('month', c)` into the statement itself, which is two sources' spelling stated as though it were every source's: BigQuery reverses the arguments and takes the unit as a bare keyword. That half is a fifth field on `Dialect`, the same move `parameter` already made for the same reason, and the reasoning the old line carried is unchanged — a unit is one of the grammar's own keywords rather than a value, and a source would need it foldable at plan time either way.

The half worth writing down is the other one. BigQuery names three truncation functions — `DATE_TRUNC`, `DATETIME_TRUNC`, `TIMESTAMP_TRUNC` — and picks by the column's type, which the builder cannot do: it knows a column's name and not its type, deliberately, because that is part of why it is testable without a source. The three ways out were to give the builder the profiles, to have the connector emit one form that covers every case, or to fold `date` and `timestamp` together for this purpose. The third breaks the value contract outright and the first widens the builder for one function's sake, so the second is what this does — but not for the reason it looked like it would need. The result set contract already decides this. A truncated value is a timestamp on both sources that shipped before BigQuery, and `test_result_set.py` holds them to it, so a BigQuery connector using `DATE_TRUNC` on a date column would answer with a date and break the contract rather than keep it. The function follows from the shape the value has to come back in, which is one form for every temporal column: `TIMESTAMP_TRUNC` over a cast. The type-dependence evaporates, and what looked like the strongest argument for widening the builder turns out to be an argument for the contract already being right. The cost is a cast on every truncated column, which BigQuery folds into the scan, and that a DATETIME is read as UTC by that cast — which is the same reading the value gets when it comes back without a zone, so nothing about it is new.

**BigQuery ships unmeasured, and says so.** Nobody has run Vizmith against a project. The connector is written from vendor documentation, its deterministic tests drive a fake client through the real client library's own parameter types, and its live tests are written and skip without one. `modified` reports None until somebody measures `__TABLES__.last_modified_time` against the streaming buffer caveat, which means the profile cache is off on a source that bills by bytes scanned — the expensive answer, chosen because the alternative is figures that are quietly out of date, which is the same standard that made Databricks pay for a `DESCRIBE DETAIL` rather than read a free field that does not move. `docs/compatibility.md` carries the row, and the row says read rather than measured.

**A credential is the vendor's file to hold, not Vizmith's.** Snowflake is where this had to be decided, because it is the first source whose client will take a password. The Databricks connector never faced it: it names a profile in `~/.databrickscfg`, which `databricks auth login` writes, so Vizmith stores which profile and never the secret. Snowflake has the same shape available — a named connection in `~/.snowflake/connections.toml` — and that is what the connector takes. The alternative was an account, a user and a password among the settings `configure` asks for, which would have put a second secret in `config.env` and made the sentence about the model key being the only one false. The cost is that somebody has to have written that file before Vizmith can read their warehouse, which is one command of the vendor's own CLI and is what they have already done if they use it. BigQuery needs nothing here, since its client resolves application default credentials by itself, and DuckDB's credential is a file path.

**Two more sources ship unmeasured, and the table says which.** Snowflake fits the interface so exactly that #168 predicted it would prove nothing, and that held: no field changed, no rule moved, and the strongest thing its tests assert is that a spec compiled for it is the same statement the other sources get, bar the parameter markers. What is its own is small and real — a NUMBER is an integer or a decimal by its scale, and a `SHOW` has to be read by column name because its columns have moved between releases. `modified` is None there for the same reason it is None on BigQuery: two candidates that do not mean the same thing, and the wrong one is silent. `docs/compatibility.md` now carries a row per source with what each answers for the contracts that have a `None` in them, and whether that row was measured or read.

**A planner statistic is not an approximate count, so PostgreSQL pays for an exact one.** Core Postgres has no `APPROX_COUNT_DISTINCT`, which makes it the first source to answer None to `approx_distinct` and the first to set `distinct_count_exact` for real. `pg_stats.n_distinct` is the free thing somebody will reach for, and it is not used. Three reasons, and the first is the one that decides it. It is a planner statistic that only exists after `ANALYZE`, so on a table nobody has analysed since a bulk load it is a figure that looks like a fact and describes a table that is gone — which is the same failure the freshness token exists to prevent, arriving through a different door. It is also not one number: it reports zero for unknown and a negative fraction for a scaled estimate, so reading it is three cases rather than a count. And taking it would mean `approx_distinct` stops being a SQL function template and becomes something a source can implement however it likes, which is a callback in the `Dialect` record for one source's sake.

So Postgres pays for `count(DISTINCT c)` per column, and the cost is stated rather than hidden: an exact distinct count per column is the scan the "a profile is cheap by requirement" rule exists to prevent, and on this source that rule cannot be kept. What that buys is that the figure is exact and the prompt says so — a reader who cannot tell a count from an estimate treats a guess as a fact — and that the second opinion stops hedging a bound it quotes. Both of those branches existed and neither had ever been produced by a source; they are exercised in CI now, through the DuckDB connector with its estimator taken away, which is cheaper than a server and proves the same thing.

**A source that declares its own keys is the good case, and the screen said so badly.** Postgres foreign keys are enforced and usually present, so `relationships()` returns facts and inference finds almost nothing. The Data view then showed two sections saying nothing was there — "Nothing is waiting for an answer", "You have not confirmed a suggestion yet" — above a long list of declared keys, which describes the person rather than the schema and reads as broken. The empty copy is conditional now: where the source declares keys and nothing is open, it says the source declared its own and there was nothing left to guess at. It is a sentence rather than a feature, and it is here because it is the first thing the fourth connector taught that had nothing to do with SQL.

**A failure after validation reaches the person as what failed, and says which part failed.** `api.py` stated that no response carries SQL, so a client cannot learn one, and a warehouse's error message often quotes the statement it refused. The message is passed on anyway, because the person reading it asked for that query, configured that source and can already read the schema, so withholding the statement removes their only clue and protects nothing. It comes back in the same `errors` list the validator's refusal uses, so the interface keeps one way to show a refusal, at 502 rather than 500 or 400, since the request was well formed and the spec was valid and what failed sits behind the server. The response also names which part refused, because a question passes through the source, the model and then the source again, and from a browser those are one request: a heading picked by guessing would put a warehouse's words under the model's name, which is the same wrong sentence this replaces. Three parts can refuse rather than two, since the builder's re-aggregation rule needs the compiled query and is the one spec rule that runs after validation rather than inside it. That one answers 400 rather than 502, because nothing behind the server was reached and the spec is what has to change, which is the same thing a validator error means and the same next move for the person reading it. The cost is that a client learns statement text wherever a source quotes it, which is worth less than a person being told to check a source and handed nothing to check it with. The model key is redacted by the adapter before anything can echo it, and that is what keeps a model's own message safe to return to a browser.

**A statement is waited on for five minutes and then cancelled.** The catalog polls while a statement is pending or running, and that loop had no end, so a statement the warehouse never finished never returned: a request holding a worker, a control that says Running with nothing after it, and a query billed for as long as it kept running with nobody left to read the answer. A cold warehouse start and a runaway query are the same thing from here, both pending and not finishing, so a cap tight enough to protect a request is one that fails the first query of the day by design. Five minutes is where that trade sits, and past it the statement is cancelled at the source and the wait is given up on, quoting how long it waited so the refusal reads as "this took longer than five minutes" rather than as a generic failure. It is a constant rather than configuration: the value a person reaches for when a query is slow is a longer one, which hides a runaway query instead of fixing it, and a cap a request carried would let a client hold a worker for as long as it liked. The cost is a classic warehouse whose start runs past five minutes, which fails the first question and answers the second, and naming the wait in the message is what makes that readable rather than mysterious. The cap covers the whole wait rather than the polling alone, since the execute call blocks for its own `wait_timeout` first and a person sat through that too. Cancelling is best effort, because the caller is already being told the statement did not finish and a source that will not take the cancellation cannot change that.

**A series past the colour order is refused, not folded and not cycled.** Series colours are assigned by position from the eight slot order, whose sequence is the colourblind safety mechanism rather than a preference, so a ninth series has no colour to take. Three answers were available. Cycling back to slot one is what ECharts does by default and it puts one colour on two entries of the same legend, which is a chart that lies about which series it is. Folding the tail into "Other" is what the data viz skill recommends and it is aggregation, which lives in the query and never in the renderer, so the renderer doing it would put a number on screen that no spec describes and no `{ } JSON` shows. What is left is to refuse: a chart whose colour channel produces more than eight series is not drawn, and the message names the count, the cap and the field that sets it, which is `limit_by.limit` on a multi series chart and `limit` on an arc. The cost is that a valid spec can be refused by the renderer, since `limit_by.limit` allows a thousand, and that the refusal arrives after the query has already run and been paid for. It is worth it because the alternative is a chart that looks finished and cannot be read, and because the rows are not lost: the Table tab shows every one of them, which is also what makes the three low contrast slots legal in the first place.

**A well infers a default, shows it, and lets it be changed.** Dropping a numeric column into Values has to choose an aggregate and dropping a date into Axis has to choose a truncation unit, and neither is in the spec until something decides. Asking at the moment of the drop was the alternative, and it makes a drag slower than typing the JSON, which removes the reason to offer dragging. So a number is summed, anything else is counted, a date on an axis is truncated to a month, and every one of those is a control in the well rather than a line in the JSON: the aggregate is a select next to the column, the unit is a select that also offers every value. That is the whole of the argument, because a default nobody can see and nobody can change is the quiet kind of wrong this project exists to avoid, and one that is visible in the panel a person is already looking at is a choice they made. The cost is that the first render after a drop is a guess, so a person who wanted an average sees a sum before they see their answer, and a chart screenshotted without reading the well can misreport what it counts.

**A drill asks what to group by, from the tables the query already reads.** Clicking a mark filters on the value that was clicked, and a filter alone gives a chart of one bar, so the narrowed question needs another dimension. The model was the natural place to get one once M4 exists, and it makes a click slow and unrepeatable, which is the same argument that put relationships in the catalog rather than in a prompt. Reading it off the relationship graph and the profiles is deterministic and occasionally baffling, and a baffling chart nobody asked for is worse than one more click. So the click opens a short menu of the non measure columns of the tables the query already reads, and nothing from another table is offered, because that would need a join a click made rather than one a person confirmed. The cost is the extra click, a menu that is empty on a single table query with one dimension, and a drill that is refused on a truncated date axis, where the label is a month and a filter on the column behind it would silently mean one day of it. The clicked value goes back as a bound parameter and a null category is filtered with `is_null` rather than compared to anything, and the spec that was replaced stays one control away, because a drill that cannot be undone is a trap.

**Source and model configuration stays server side, in a file, read at startup.** The design described a Setup screen that sets the source, and `api.py` states that a request cannot name a database, and those cannot both be right. Configuration stays where it is. A request that cannot name a database is a request that cannot be pointed at one, which is one sentence in a governance review and costs nothing to keep, and the middle option, an endpoint bound to loopback that writes the server's own configuration file, adds the first endpoint in this API that changes server state, for a convenience rather than for a capability. The cost is real and is not waved away: Vizmith runs on a person's own machine and serves their own browser, so telling them to edit `.env` and restart a process is asking them to be an operator to use a local application, which is not where the packaging direction points. What that buys is that the whole surface stays read only apart from one relationship answer, and that the model key never has a path into a browser at all, rather than a rule saying it must not come back out of one. So the Setup component of the design is cut rather than corrected, and the interface says what is missing and what to do about it in one place, in the canvas, instead of in a placeholder and a panel note with different wording. Both pills are in the chrome, since `/api/health` already reports both. Revisit when there is a packaged build, because that is when a first run has nobody to tell about a file.

**A question in the eval set carries a reference spec, and the expected rows are what running it produces.** A stored result set was the other option, and it is a copy of the fixture data that stops being true the moment the generator is run again, which fails every question at once for a reason that has nothing to do with the prompt. A reference is a spec that already lives in the fixtures, compiled by the same builder and run against the same source as the answer being scored, so what is compared is two result sets produced the same way. The cost is a second query per question, which is why it sits in the third layer rather than the first. It also forces the questions to be written out in full: an expected result set is only an expectation where the question determines it, so a filter the answer has to apply is named in the question rather than left to be guessed and then marked wrong for guessing. "Which ten countries produced the most revenue" therefore says which orders count and from when, which reads as a stilted way to ask and is the difference between scoring the translation into a spec and scoring telepathy. Every question is also checked to have no tie where its limit cuts, since a tie makes two correct answers differ and marks one of them wrong.

**The layers are ordered by what they cost, and a failed layer ends the question.** Validating costs nothing beyond the answer already paid for, reading the spec's tables and columns costs nothing, comparing result sets is two queries against a warehouse, and judging the mark reads rows that are already in hand. Running them in that order means a hopeless answer is refused before anything is billed for it, and stopping at the first failure is what makes the report readable: whether the right rows came back from a spec that names the wrong table is not information, so a score of three out of four with a hole in the middle would say less than a score of one that names where it stopped. What that costs is that one run cannot tell whether a question that fails layer 2 would also have failed layer 4, and the answer to that is to fix layer 2 and run it again, which is what the cache makes cheap. The tables and columns a question expects are a floor rather than an exact match: an answer that also reads a table nobody asked for either changes the rows, which the layer below catches, or does not, and failing it for the second case would score a preference. The extra is recorded on the score instead, so it is visible in the run rather than invisible in the number.

**A cached answer is keyed on the prompt, not on the question.** The harness exists to make a prompt change measurable, so a cache that answered the new instructions out of the old ones would report a score the new prompt never earned, and it would do it silently and for every question at once. The key is the first prompt of a question with the model name and the endpoint, which means changing a word in the instructions, changing what a profile says, or pointing at another endpoint all pay for the answers again, and re-running the same set against the same everything is free. Only the first prompt is the key: the retry loop's later prompts quote the validator about an answer that is not in the cache, so keying on one would be keying on something the next run cannot reproduce. The cost is that the cheapest way to re-measure is also the one that never changes, and a run that is entirely cached is a run that asked nothing, which is why the record counts how many questions were actually asked.

**A mark is judged by one rule against the shape of the result, and the rule refuses rather than ranks.** Several marks suit most shapes, so a layer that named the best one would score a preference and would move whenever somebody's taste did. What it refuses instead are the combinations that misread the data: an arc on a time axis, which throws away the only thing a time axis has; a line or an area over categories, which draws the gaps between them as if they meant something; a bar on a quantitative axis, which turns a measure into categories; an arc carrying a colour channel, which has no second ring to put it in. Row count is part of the shape rather than a separate rule, so an arc of ten slices is refused at the same cap the renderer refuses a ninth series at, and for the same reason: past it the chart is drawn and cannot be read. A spec with no `x` is a figure, and `mark` says nothing on one, so there is nothing there to defend. The cost is that this layer encodes a judgement, and where that judgement is wrong the run says so about a chart that is fine — which is why it is one rule in one place, argued in one paragraph, rather than a list of acceptable marks per question that nobody would keep true.

**A dashboard is several specs under a name, and the name is what identifies it.** The other option was a generated id with the name as a label on it, which survives a rename and is what most software does. It was not taken. The stored file is the whole of a dashboard, and under ids it reads as a list of hex strings with the recognisable part buried in each entry, which matters because this file sits in a state directory a person can open, beside the relationship answers they can already read. Under names it reads as what they saved. What that costs is that two dashboards cannot share a name, and that renaming is saving under the new name and deleting the old, which is two steps for something that should be one. It also puts the name in a URL, so a slash and a control character are refused rather than escaped, since a name that addresses the thing has to be able to address it. The tiles are a list rather than a set of positions, because the arrangement is an order and a width — one column or both — and a canvas of pixel coordinates would be a stored geometry that is wrong on the next screen and a second layout engine to keep true. A tile holds a spec and never a row: rows belong to the source, and a stored copy of them is a number that stops being true without saying so, so opening a dashboard runs every tile through `/api/execute` exactly as a single chart runs, one statement per tile, which is what the tile cap exists to bound. Every tile is validated before it is stored, because a store that took an unvalidated spec would move the refusal from the save a person is watching to an open they are not.

**The write surface is specs and answers about them, never configuration.** The entry above about Setup said the whole surface stays read only apart from one relationship answer, and dashboards make that two writes rather than one, so it is restated rather than left to be discovered. What a request may now change is what a person said about a suggested join and which specs they saved together. What it still cannot do is name a database, a warehouse, a model endpoint or a key: those come from a file the server reads at startup, and nothing over HTTP writes them. That is the sentence a governance review reads, and it is intact. The cost of the second write is a file the server owns whose format has to keep working across versions, and unlike the profile cache it cannot be dropped when it does not: a cache that throws itself away costs one more profile, and a dashboard that throws itself away costs work nobody can get back, so an unreadable file raises rather than starting empty and being overwritten by the next save.

**A packaged Vizmith configures itself with a command, and still never through the browser.** The Setup decision above said to revisit this when there was a packaged build, because that is when a first run has nobody to tell about a file, and there is one now: the wheel carries the built interface inside the package, so an installed Vizmith serves its own frontend and `uvx vizmith serve` is the whole of starting it. That changes what the alternative to a browser-written configuration is. It is no longer "edit the file you already have open in the checkout you are working in", it is "find where this thing keeps its files", which is worse, and it is the reason the middle option was tempting. It is still not taken. A first run screen that posts configuration to the server would be the first endpoint in this API that changes server state, and it would put a model key on a path that touches a browser, which is the one thing the whole design has never had to write a rule about. `vizmith configure` answers the same need without either: it asks in a terminal, it writes a file the server owns in the state directory beside the profiles and the dashboards, and it writes it readable by its owner alone, because one of those values is a key. `--show` prints where each setting is coming from and never what it is set to. The order is environment, then `.env` found from the working directory upwards, then that file, so a checkout keeps behaving exactly as the README always said it did and nothing anybody has already set moves. What this costs is a command a person has to run and a restart they have to do, which is a smaller cost than a configuration endpoint, and the sentence that a request cannot name a database survives another milestone. Building a wheel now needs Node, since the interface is built into it rather than committed as an artefact nobody reviews; that is paid by whoever releases and not by whoever installs, and an editable install skips it and falls back to `web/dist`.

**A tile is corrected in the Chart view, and goes back only when it is asked to.** A tile holds a spec, and until now there was no way back to it: correcting a filter meant rebuilding the chart, adding it, deleting the old tile and moving the new one into place. Where the correction happens was the first question, and editing in place on the dashboard was the wrong answer — it needs the wells and `{ } JSON` in a second view, which is a second editor to keep true, and the first one is where the person built the chart in the first place. So a tile opens into the Chart view carrying its spec. The second question is what happens to the tile while that is going on. Replacing it on every run is what a live binding would do, and it means a half typed spec becomes the tile, so a dashboard changes under somebody who is looking at something else; it also makes abandoning an edit impossible, since the thing to go back to has already been overwritten. So the correction goes back when it is asked to and not before, with Never mind next to it, which is the same rule the drill already follows: a change that cannot be undone is a trap. What that costs is one more click and a state the interface has to show rather than hold quietly, so the tile being corrected is marked on the grid and named in the strip under the chart. The tile is held by reference rather than by position, because a person can reorder or remove tiles while one is being corrected, and a position would go on pointing at whatever moved into that slot — the correction would land in a different chart, and both of them draw, so nothing would say so. A tile that was removed while it was being corrected is not added back either, since removing it was also something they asked for.

**Renaming is a save and a delete, done in that order by one control.** The name identifies a dashboard, and the entry above admits what that costs: renaming is saving under the new name and forgetting the old one, which is two steps for something a person thinks of as one, and nothing in the interface offered either. It is one button now, and it is still those two calls — no endpoint was added, because a rename endpoint would be a second way to write the same file. The order is deliberate: the save goes first, so a refusal leaves the dashboard where it was rather than deleting it and then failing to write the replacement. The cost is that a rename which fails halfway leaves two dashboards rather than one, which is visible in the list and fixable with the Delete next to it, and is the better of the two ways to fail.

**The double that stands in for a source has to keep the promise the source makes.** #166 was a tile drawing "No rows to draw" for a spec that returns thirty, seen once and not reproducible, and filed as an observation rather than a defect. It is real, it reproduces about once in four runs of the browser suite, and it was the harness rather than Vizmith. A DuckDB connection is a single cursor and the suite shares one; `FixtureCatalog` held its serialising lock on the instance, and the interface fixture built one catalog per request — so two tiles of a dashboard fetching at once were two threads with two locks interleaving `execute` and `fetchall` on one cursor, and one of them came back with the other's rows or with none. What makes this worth an entry rather than a one line fix is which promise was broken: `run` says on the `Catalog` protocol that it is callable from several threads at once, every shipping connector makes that true, `source()` builds one connector for the process, and the double did neither. A double that is easier to satisfy than the interface it stands for turns a suite into evidence about the double. The lock is now one lock for every catalog over that connection, the served application holds one catalog the way a running one does, and the race has a test of its own that fails deterministically without either.

**A few flows are driven in a browser, in CI, in a job of their own.** Every other frontend test is a static render: it reaches the first frame and cannot press anything, which is fast, deterministic and blind to the one class of failure that only exists between interactions. The dashboard work shipped one of those and the whole suite stayed green — the arrangement lived inside the view that drew it, so going back to the Chart view to build the second chart threw the first tile away, and the feature was broken in exactly the flow it exists for. It was found by hand. So a browser suite exists, and the argument is about where it runs. Out of CI it is honest and unrun, which is the same as not having it. In CI it costs a browser download per run and admits a test that can go red for the runner's reasons rather than the change's, so it is a second job rather than a step inside the existing one: a flake in a browser then reads as a browser failing rather than as the offline suite failing, and the fast gate keeps its meaning. What keeps the cost bounded is that this is deliberately a handful of flows rather than a mirror of the unit tests — a browser suite that tests controls is slow twice over and gets deleted the first time somebody has to fix it in a hurry. It drives the real server over the committed fixture data with the source dependency replaced, so it needs no warehouse, no network and no credential, and it drives the built frontend, so it skips where `npm run build` has not run. `VIZMITH_CHROMIUM` names a browser where Playwright's own copy is not the one installed, which is what makes it runnable in a container that already has one.

**Whether a thing is a spec is the browser's question; whether it is legal is the validator's.** The interface deliberately holds no second opinion about a spec — `/api/validate` is the judge, and an opinion in the browser is one that can disagree with the one that counts. What that left unanswered is the question the browser has to answer before it can render anything: whether the value in hand is shaped like a spec at all. `{"a":1}` parses, is an object, and has no `chart`, and every panel read `draft.chart.encoding` without asking, so typing it into `{ } JSON` threw during render. A throw during render unmounts the tree in React 19, so what was lost was the whole application, and the reload that recovered it was also what discarded the spec in the editor. Those are different questions and answering the second one in `draftIn` is not a second validator: it checks the parts a panel dereferences — the query, the chart, the chart's encoding — and says nothing about their contents, so a spec with an unknown mark still reaches the validator to be refused by name. What it costs is that a spec being typed goes quiet in the wells sooner, which is what a half typed spec should do to them. Beside it, and independent of it, two error boundaries: one around the canvas and one around the application, because a render that throws for a reason nobody predicted should cost the chart or the tab's contents rather than the tab, and should say what happened — the person who hit it is the one who can report it, and a blank page reports nothing.

**One region announces the outcome, and it says what the canvas shows rather than narrating the way there.** Every message this interface produced appeared by being swapped into the tree, which a screen reader does not report: the wait, which is the only signal during a first question and the one the interface itself says can be slow; the refusal, with the validator's or the source's own words; the chart. WCAG 4.1.3, level AA. The surrounding code was never careless about this — `aria-label`, `aria-pressed` and `aria-expanded` are used throughout, a custom row carries Enter and Space with a comment saying why, and provenance refuses to be colour alone — live regions are the class this had not reached rather than one it decided against. What made it worth arguing about is that a region saying too much is worse than none, and this canvas changes on every drop into a well. So: one region, polite, carrying one sentence — the wait, the row count, or the refusal's heading and its first line, since the full list is already on screen and reading it aloud per keystroke of a drag is how a person turns announcements off. The badge in the strip stays silent because it is a second account of the same outcome. The two refusals that arrive with no focus change — a well's, which answers a drop, and the dashboard's, where a refused save and a successful one were equally silent — are alerts, and the dashboard's "Saved as …" is polite beside it, because agreement can wait for a gap and a refusal cannot. A tile's own state is not announced at all: a dashboard holds up to 24 of them and they resolve together, so a region per tile is 24 sentences for one gesture. The rail moved from `aria-pressed` to `aria-current`, which is what three buttons that choose a view actually are. The keyboard path for dragging is a different and much larger piece of work, and is still open.

**A critique may say what is refusable, and the model's part is naming the replacement the rule will not.** The deferred entry said this waits for M5, because without evaluation there is no way to tell whether its suggestions are good. M5 landed, and the question it left is where the line sits. The wide version suggests a different question — a better dimension, a filter somebody forgot — and it is the one people want and the one that cannot be defended: it scores a preference, it moves whenever somebody's taste does, and no run can say whether it held. The entry above about the mark layer already refused to name a best mark for exactly that reason. So the narrow version ships. What a critique may name is what a rule refuses, which today is one rule: a mark the shape of the result contradicts, in the same sentence the eval harness's fourth layer uses, because `misreads` in `critique.py` is that rule and `indefensible` is it applied to the rows the harness already fetched. Two implementations would be a harness that refuses what an assistant approves of.

That leaves the obvious objection: if the finding is a rule, why is there a model in this at all. Because the rule refuses and does not rank. Several marks suit most shapes, so naming the replacement is the preference this whole design refuses to write down as code — and it is also the thing a person actually wants. It is asked for instead, it comes back as a proposal beside the spec rather than a change to it, and the person takes it or leaves it. That is the one judgement in the feature that is not a rule, and it is why `/api/critique` answers with two specs and applies neither.

What it buys over the fourth layer is when it runs. The harness counts the rows it fetched; a critique reads the profiles, so an arc nobody can read is named before the query has been paid for. What that costs is that a profile bounds a row count rather than counting one, and a distinct count is usually approximate, so a finding quotes an upper bound and says where the bound came from. Where nothing bounds it below the query's own limit, nothing is claimed: a limit of 500 over a column with four values is four slices, and a finding made out of the 500 would name a problem that is not there. A truncated date is the same refusal — the buckets are fewer than the column's values by an amount nothing here knows, and an arc over time is refused for its axis anyway, which is the better sentence.

The suggestion may change the chart and nothing else. The query is the question the person asked, so a suggestion whose query is not the one it was given is refused here rather than shown, which also makes it measurable for free: the rows cannot have moved, so `vizmith eval --repair` asks the critique wherever the fourth layer refused a mark and scores the answer against the rows that question already fetched. That number, `repaired` out of `critiqued`, is what says whether the suggestions help rather than asserting it. Waiting for #61 to have run first would have been the stricter order, and it is not what this waits on: what #61 measures is the prompt that writes a spec, and what this measures is a different prompt over a spec that already exists, with its own counter in the same record.

What is deliberately not said. A colour channel whose dimension outruns the eight slot colour order is a real refusal and it is not a finding here, because the fix is `limit_by.limit` and that is in the query; the renderer already refuses it by name, at the point where the count is known rather than bounded. If the wide version is ever wanted, it is a different feature with a different argument, and the thing to notice is that it cannot use this file's word "refusable" to justify itself.

**Hosted API first, self hosted second.** Both are targets, but development happens against a hosted OpenAI-compatible endpoint because structured output is reliable there. Small local models fail schema validation more often, which makes the retry loop the dominant UX. That loop gets designed once the schema is proven, not before.

## Milestones

**M1, spec and renderer.** JSON Schema, semantic validator, golden fixtures, ECharts renderer driven by those fixtures. No database, no LLM. Done when a spec file renders a correct chart and every invalid fixture is rejected for the right reason.

**M2, catalog and profiler.** Unity Catalog connector over the synthetic fixture dataset loaded into a workspace. Types, cardinality, null rate, min/max, distinct samples for low cardinality columns. Deterministic and cacheable. Done when the profile of a fixed schema is byte identical across runs.

**M3, query builder.** Query IR to SQL, executed against a SQL warehouse. Done when every valid fixture returns a result set the renderer accepts.

**M4, LLM adapter.** OpenAI-compatible `base_url`, user supplied key and endpoint. Question plus profile in, spec out, validated, rejected and retried on failure with the validator errors as feedback. Structured output support differs across providers; what that check found is recorded above.

**M5, eval harness.** A fixture question set scored for correctness. This is what makes prompt changes measurable instead of anecdotal.

**M6, dashboards.** Several specs saved together, arranged, reloaded.

## Deferred

**A second connector.** The catalog is still an interface with one implementation behind it, because the layers above it must not learn Databricks vocabulary. Anything else, DuckDB included, waits until somebody has a reason to run it.

**Rebuilding a dashboard from a screenshot.** Needs a vision model. Vision support across self hosted OpenAI-compatible servers is uneven, so this breaks the single adapter assumption. Revisit after M6.

**Critiquing a dashboard rather than a chart.** The critique above is about one spec. A set of charts needs an argument about what a set is for — whether two tiles answering the same question is a fault, whether an arrangement can be wrong — and nothing in the project has one yet. It is not the chart rule applied several times.
